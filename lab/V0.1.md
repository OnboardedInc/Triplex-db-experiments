give it more budget, but lets work towards a v0.1 of this project and keep our budget for now".

## What version 0.1 is

One branch, one database, one scorecard, one playground.

1. **One branch.** Everything the product needs is merged on one branch (`exp/DX-INT1` today), builds from a clean
   clone with one command, and passes its correctness gates. Work that is not merged there is not in version 0.1.
2. **One database.** Every account lives in one Datomic database on Postgres storage: ten deep accounts of 100,000
   people, wide thin accounts, and small accounts.
3. **One scorecard.** One command runs the fixed workload on a bare-metal server and prints, for each of the nine
   priorities, the bar, the measured number and pass or fail. It runs twice: on the fresh database, and on the same
   database aged to 1 billion records.

4. **One playground** (Sam, 2026-11-20, messages below). One command starts the product on a laptop, loads an
   invented test data set, and serves two things on the local machine only:
   - **A dashboard** to query the data and change it and see what comes back and how long each step took: current
     values, values at an earlier point in time, a person's history, a save and its receipt, the change feed,
     Publish, erasure, a native query.
   - **A local API** that local agents can call to do the same things, with a machine-readable description.

Sam's words on the playground: "v0.1 will also come with a "demo playground dashboard" which should be able to load a
bunch of test data we store as a blob or w/e in github and then the dashboard helps you query and try to change things
and etc to play around with it and see times and return records and etc. Also it should expose APIs on a local server
that lets your local agents call the local server to query and etc".

Sam's answers on the test data, same day (a customer's name is replaced by "[the reference account]"): "is there
somewhere else we can put the test data? 25MB isn't that much data right? Somewhere in cloudflare?" and "the data is
invented, but in the shape of an onboarded account, so use real onboarded account structure" and "at least two big
accounts with deep history (more than 1 month, lets do like 2GB-5GB of data), one [the reference account] shaped and
scale, one thin and wide but on the scale of [the reference account] shaped and scale."

The test data set, as the orchestrator reads those answers:

- **Structure:** how Onboarded stores an account (employer, clients, job types, employees, placements, tasks,
  subtasks, field values, custom values, files, forms). Every value is invented by a seeded generator.
- **Full set, 2 to 5 GB, in Cloudflare object storage:** one deep account at the reference account's shape and scale
  (about 100,000 people, about 160 facts each), one wide thin account with the same total number of facts spread
  over millions of people, a few small accounts, all in one database, with more than one month of save history.
- **Small set, at most 25 MB, in the repository:** the same structure with fewer people, for tests and a quick start.

Version 0.1 is finished when the scorecard has run on the merged branch at both ages, every failing line has a
written cause and a next step, and the playground starts from a clean clone with one command. It does not require
every scorecard line to pass.

## Decisions for version 0.1 (Sam, 2026-11-21)

- **Machine loss:** version 0.1 uses option B: after a machine is lost, new saves are held until a second copy of the
  data exists. Reads continue. No confirmed save can be lost to a second failure. Writes can stay held for minutes at
  full size, so the 60-second bar is knowingly not met by B at that size. Option C (three machines; both bars) is the
  plan for version 1.0. Measured on two rented machines on 2026-11-23 at full size and 235 saves per second: no
  confirmed save lost, reads unbroken (longest gap 47 ms), detect, fence and promote in 1.5 s, first protected save
  after 603 s (a local copy of 131 s and a SHA-256 check of 452 s). Sam, 2026-11-23: "keep Option B for 0.1 for now".
- **Quiet account bar (priority 6):** met when the ratio is at most 1.25 or the quiet account's loaded commit p99
  stays at or under 50 ms (`lab/TARGETS.md`).
- **Lookup by the value of a protected field** (for example finding a person by SSN) is not needed once an account
  has a removal policy, and never will be. Data can be marked sensitive or redacted, and queries by its value are
  refused. The typed refusal stays.
- **Order of work:** the server first ("get the server as good as we can"); the playground after that.
- **Realistic data set:** tests should run on a realistic data set (the ten deep accounts, the wide thin account and
  the hundred small accounts in one database) "sooner rather than later", added "whenever it starts to make sense".
- **Budget:** stays at $200.

## What is deferred past version 0.1

- **Version 1.0 (Sam, 2026-11-21): three-machine failover (option C)**, about $314 a month for the third machine in
  the example sizing; needs a provider that allows three servers.

- **A future version (Sam, 2026-11-23): failover option A on the roadmap** ("Lets put Option A for failover for a
  future version on the roadmap"). Option A accepts saves on one copy after a machine is lost and rebuilds the second
  copy behind them. Measured on 2026-11-23 at full size and 235 saves per second: no confirmed save lost at the first
  failure, first new save after 19.5 s (inside the 60-second bar), reads unbroken. Its cost is the window in which new
  saves sit on one machine; how many a second failure in that window would lose is not yet measured (the check stopped
  on a test fault).

## Budget

The cloud budget stays at $200. Server time goes first to the three measurements version 0.1 cannot be judged
without: the per-person writer against the grouped writer on ten accounts in one database, the scorecard on the
merged branch, and the 1 billion record rung.
