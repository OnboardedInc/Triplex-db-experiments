## F1 remaining — High: three in-scope adapters still return mixed-cut closures

**Primary location:** `packages/core/src/store/TriplesLive.ts:572–577`. An absent `pullPosition` leaves `resolved.recordedPosition` undefined; every fallback level remains free to read a different committed state. The implementation correctly propagates a supplied position, but does not supply one for these adapters:

| Adapter | Relevant location | Outside-transaction behavior |
| --- | --- | --- |
| XTDB | `packages/xtdb/src/XtdbStorageAdapter.ts:187–192` | Takes the position only from `basis.recordedPosition`; without it the generated SQL has no position cut. Each query reads its current native snapshot. |
| Datomic | `packages/datomic/src/DatomicStorageAdapter.ts:69–85` | Sends the basis to `client.rows` but no held handle outside a transaction. `gateway/main.clj:74–86` synchronizes a fresh database value for requests without a handle; `gateway/storage.clj:149–156` applies only the supplied position or handle. Native immutable DB values are per request here, not shared across the pull. |
| Non-broker QLever | `packages/qlever/src/QleverStorageAdapter.ts:163–166` | Takes the position only from the basis; without it each SPARQL request reads the then-current graph. This includes the adapter's non-broker mode, rather than its delegated broker configuration. |

**Reproduction:** [round4-review.test.ts](round4-review.test.ts:207) drives the actual three storage adapters and public `Triples.reach` against an offline native-response fixture. Commit 1 has `root -> target`, `target = 1`. After the root query's response is captured, the fixture advances atomically to commit 2, which retracts the root reference and replaces the target value with 2. Both commits have recordedAt 1000. `T.reach(root, { validAt: 2000, recordedAt: 1000 })` returns `root -> target` plus `target = 2` on **all three adapters**. No cut contains that closure: commit 1 contains value 1; commit 2 has an empty root closure.

For each adapter the same fixture also runs an explicit-position control, supplying a test-only `pullPosition` implementation that captures the current position once. The native SQL/SPARQL/request handling honors that cut and returns the whole old graph. Raw witnesses record two unpinned requests at heads 1 and 2 versus two pinned requests at position 1. The fixture does not invent a cut-independent response: it parses the position predicate generated by XTDB/QLever or the basis forwarded by Datomic and selects the matching snapshot.

These are **offline adapter/request reproductions**, supported by source inspection, not live-engine or public-native-write executions. The public-write broker reproduction and its corrected expectations are separately exercised by the builder's tests. No claim is made about engine throughput or live deployment.

**Proposed fix:** provide transaction-aware exact-cut handling on these three in-scope paths, using their existing position support or a held snapshot for the whole pull, while preserving staged reads and writer progress. Alternatively, refuse an unpinned pull when it cannot promise a coherent closure. Add the same commit-between-levels and same-timestamp checks for each path, with pinned, staged-transaction and post-commit controls. Do not use the absence of a hook as permission to silently return a mixed graph. No product fix was made in this review.

## Broker and KV fix assessment

The broker/KV changes are sound within the exercised offline scope and need not be reverted to address the remaining adapters:

- `TriplesLive.reach` calls `pullPosition()` once, before `getReachTriples`, adds a supplied position to one resolved basis, and uses that same basis for both the direct attempt and every `entitiesAt` fallback level.
- Broker `pullPosition` at `BrokerStorageAdapter.ts:984–992` returns undefined inside a transaction, the existing caller cut inside `withCurrentPull`, initializes a previously unpinned context on its first read, or returns the head outside either context. Transaction precedence prevents an old outer context from hiding staged rows.
- The 11 builder broker tests pass, including the ported public-commit reproduction with corrected expectations, commits after levels one and two, record-time fallback with equal timestamps, the direct route, an explicit caller pin, and staged reads with H1 off/on.
- An additional reviewer test lets the direct H1 attempt read the old graph, **awaits a real public writer commit**, then deliberately declines the attempt. `pullPosition` is called exactly once; the direct attempt and all three fallback levels receive position **2048**, despite the head advancing to **3072**. The result is the whole old graph. The writer completed while the pull was active, rather than waiting for that pull to finish.
- An additional context test starts `withCurrentPull` without an explicit position, reads once, commits a retraction, and reads again. Both pulls retain the original cut; outside the context the next pull sees the new state. Inside a transaction nested in that context, `pullPosition` returns undefined.
- KV `reach` and multi-entity `entities` capture `currentKvCommitPosition` once. Position-aware visibility checks exclude later assertions and retain assertions retired after the captured cut. The commit counter and datoms share the backend write transaction. The five new KV regressions pass, including injection after a range scan but before subsequent metadata/materialization work.

The fix introduces no read lock or mutex around a walk. The injected writer is awaited before the read can continue, so those tests reject a writer-blocking implementation. This verifies the new mechanism; it does not substitute for a live P1 contention measurement on every backend.
