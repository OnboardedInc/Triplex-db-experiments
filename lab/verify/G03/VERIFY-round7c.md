## F5 — Medium: the stage-10 terminal write remains outside the retention guard

Location: `lab/bin/ns-run.mjs:154`; retention setup at 156–159 and catch at 178–187. Cleanup: `lab/bin/box.mjs:263` and `lab/experiments/EXP-G03/ns/smoke.mjs:42` / `exclusive.mjs:26`.

After catching a real execControl rejection, the coordinator constructs its terminal and synchronously appends stage 10 before entering the new retention try/catch. An I/O error at this boundary rejects runBoxedNS without stopping/exporting or detaching its evidence volumes. The caller's ordinary box.close() still deletes those volumes. The original control failure is replaced by the append error; the error has no terminal, runId, retained-volume or raw-directory fields.

Reproduction: `round7c/stage-review.mjs stage-10 <new-empty-output-directory>` executes unchanged ns-run.mjs and Box.execControl bytes through the builder's trusted lifecycle model and the real FaultInjector. The valid before-effect hook encounters a contradictory DR snapshot (checkpoint 1 instead of 0), so execControl rejects. A one-shot fs.appendFileSync EIO is injected only for the stage-10 append; later gap writes would work. `stage-10-attempt2.json` and its durable observation show `INJECT-stage-10`, last persisted stage 9, no walk, no raw export, no gap, no retained volumes, and all nine forensic volumes deleted by model close(). The unchanged baseline exports eight digest-matching files before DRIVER-CONTROL-FAILURE. Stage-11 and stage-12 append faults retain all nine volumes and write a gap, isolating stage 10 as the unguarded edge.

This models host I/O failure, not a candidate gaining access to the coordinator filesystem. It directly affects the promised failed-attempt retention behavior. The model's cleanup policy matches BoxExecutor.close(): every still-owned resource is removed. No real Docker volume was destroyed by this reproduction.

Proposed fix: establish the retention guard before terminal construction/logging, and include stage 10 in it. A terminal/stage persistence failure must detach the forensic volumes before caller cleanup, retain the original control cause where possible, and record the persistence gap. Add a coordinator regression for a one-shot stage-10 append failure that asserts preserved ownership after close().

## F6 — Low: a null control envelope crashes the coordinator outside its rejection path

Location: `lab/bin/box.mjs:138`, the stdout data callback's `row.schema` access. Related await: `lab/bin/ns-run.mjs:150`.

`JSON.parse('null')` succeeds, then row.schema throws a TypeError directly in the stream callback. The promise does not reject through fail()/error.partial, so the coordinator's catch and terminal/export/retention handling do not run. The fresh `null-envelope` subprocess exits 1 with `TypeError: Cannot read properties of null (reading 'schema')`, rather than DRIVER-CONTROL-FAILURE. Its durable attempt has only preterminal stage/input files, with no raw export or gap.

Reproduction: `round7c/stage-review.mjs null-envelope <new-empty-output-directory>` feeds `null\n` through the exact Box.execControl handler, with the trusted child-stream model as the sole substituted producer. This is well-formed JSON with a malformed control envelope. Current guarded driver code does not normally emit it, and no candidate route to that private pipe was demonstrated; severity is low for that reason. Existing invalid-JSON tests use an unparsable string and do not cover this callback exception.

Proposed fix: validate the parsed top-level value before property access and route malformed envelopes through fail(), preserving partial bytes. Cover JSON null and malformed object/envelope values in a subprocess regression that requires a failed coordinator terminal plus export or retained ownership, rather than merely a nonzero process exit.

## F7 — Low: partial control streams are re-encoded before the “raw” export

Location: `lab/bin/box.mjs:138`–140 (Buffer chunks appended to JavaScript strings, then Buffer.from); stdout/stderr initialization at 135.

A fresh malformed-producer fixture supplies the two bytes `ff 0a`. execControl correctly rejects with FAULT-CONTROL-JSON, but `stdout += b` decodes the invalid UTF-8 byte to U+FFFD. The coordinator exports four bytes `ef bf bd 0a`; terminal.controlFailure.partial.stdoutBytes reports 4, and both terminal/capture digests authenticate those replacement bytes. Matching exported-file digests establish internal consistency but do not establish equality to the received stream.

Reproduction: `round7c/stage-review.mjs nonutf8-envelope <new-empty-output-directory>` uses the exact Box/coordinator with a trusted PassThrough producer. `round7c/stream-review.mjs` checks the retained attempt: supplied SHA256 `e4688624e5f1ad0629505e6768e3bb36244f2f3e33e751215afa820334a76ed3`, exported SHA256 `8d75cfafa290dea108e554948eae67ba5c418cad73059f9452ff6fc652d5c869`, correct run/terminal binding, and capture/terminal equality to the rewritten bytes. The run refuses, exports eight files, and returns no result. No candidate control of this pipe or normal-driver production of these malformed bytes was demonstrated, so this is a low-severity forensic-fidelity issue, not a false qualification.

Proposed fix: retain bounded raw Buffer chunks separately from JSON decoding; construct partial streams, byte counts and export digests from those original chunks. Use a decoder/framing method that also handles multibyte UTF-8 characters split between chunks. Add byte-for-byte stdout/stderr regression fixtures for malformed UTF-8 and split multibyte characters, alongside the existing digest self-consistency checks.
