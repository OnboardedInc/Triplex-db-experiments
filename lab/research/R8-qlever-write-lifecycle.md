## 1. Idempotent re-apply after partial failure

### 1.1 Verdict

1. **Re-send converges.** After a timed-out or failed update that left some permutations updated and others not, re-sending the identical update (INSERT or DELETE) with no timeout returned HTTP 200 and left all six permutations complete (inserts) or empty (deletes). I reproduced this with partial states in the insert path (5 of 6 permutations, and 2 of 6), in the delete path, after a restart, and after a rebuild.
2. **A restart clears the junk of a single failed operation.** The persisted file `idx.update-triples` is written from the two hash sets (inserted, deleted), and the hash sets are marked only after all six permutations were updated, so partial located triples are never persisted. After the restart the junk was gone (372-byte file, all counts zero).
3. **`rebuild-index` copies the partial permutations into the new index.** Each permutation is rewritten independently from its own base blocks plus its own located triples. A state with the junk in PSO and POS only produced a new index with the junk in PSO and POS only. The next re-send healed it; a second rebuild and a restart stayed consistent.
4. **HTTP 429 does not mean "not applied".** Four outcomes exist after a timeout: nothing applied; partial and in memory only; fully committed and durable (observed: all six permutations present and still present after a restart); and, for the INSERT DATA path with new IRIs, the timeout often does not fire at all (HTTP 200 after 12 to 20 s with a 11.4 to 12.0 s limit).
5. **Client disconnect does not cancel an update.** A client that closed the socket 0.3 s after sending a 2M-triple update still got the full update applied and persisted.

Confidence: High that re-send converges (source and six probes agree), Medium on the INSERT DATA path (the same function runs, but I could not hit its 130 ms partial window with a timeout, see 1.3).

### 1.2 Evidence: source

- Cancellation is only checked between permutations: `locateAndAddTriples` loops over the six permutations and calls `throwIfCancelled()` after locating and after adding (`src/index/DeltaTriples.cpp:200-222 @ 6c5861a`), in the fixed order PSO, POS, SPO, SOP, OPS, OSP (`src/index/Permutation.h:53-54 @ 6c5861a`). [S]
- The duplicate filter uses the hash set, and the hash set is marked last: `modifyTriplesImpl` erases triples already in the target set (`DeltaTriples.cpp:461`), erases the inverse-set entries (`:468`), then calls `locateAndAddTriples`, and only then marks (`:478`). A cancelled first attempt therefore leaves nothing in the hash set, so the second attempt is not filtered. [S]
- Re-adding is idempotent per permutation: located triples live in a `SortedSequence` keyed by the triple, and "only the last inserted element for each projected key is retained" (`src/util/SortedSequence.h:22-27, 91-112 @ 6c5861a`, used at `src/index/LocatedTriples.cpp:379-384 @ 6c5861a`). A later delete of the same key replaces an earlier insert and vice versa. [S]
- `executeUpdate` inserts and deletes with `Consolidate::No` and consolidates once at the end (`src/engine/ExecuteUpdate.cpp:28-43 @ 6c5861a`), so a cancelled attempt leaves unconsolidated junk in the mutable state that the next successful update consolidates and publishes. [S]
- Persistence writes only the hash sets (`DeltaTriples.cpp:648-670 @ 6c5861a`), and the replay at start goes through `insertTriples` and `deleteTriples` again (`DeltaTriples.cpp:674-710`), so a restart rebuilds all six permutations consistently. [S]
- The rebuild materializes each permutation from its own located triples: `createPermutationWriterTask` calls `readIndexAndRemap(permutation, ..., locatedTriplesSharedState, ...)` per permutation (`src/index/IndexRebuilder.cpp:388-425 @ 6c5861a`), from the published snapshot taken at the start (`src/libqlever/Qlever.cpp:754-766 @ 6c5861a`). Only the swap diff is computed from SPO alone (`DeltaTriples.cpp:873`). [S]
- The timeout is a cancellation flag raised by a timer; the HTTP handler awaits the update thread (`src/engine/Server.cpp:1338-1415 @ 6c5861a`). If the flag is raised after the last `throwIfCancelled`, the update completes and persists, and the awaiting coroutine can still answer 429. [S][P]

### 1.4 Design implication

- **Reconcile by re-sending the identical update until it returns 200.** HTTP 200 means all six permutations were updated, consolidated and published (`modify` publishes the snapshot only after the whole function returned, `DeltaTriples.cpp:516-565`). No read-back through one permutation can prove that; a 200 can.
- **Treat every non-200, every connection error and every timeout as "unknown".** Never use 429 as proof of failure (S4) and never use a read-back as proof of success.
- **Gate `rebuild-index` on "last update returned 200 and no position is pending".** A rebuild takes the published snapshot, so a rebuild that starts while an unreconciled partial state is published bakes the partial permutations in (S3). Re-sending afterwards still heals, so this is a hygiene rule rather than a correctness hole, as long as every failed request is eventually re-sent.
- **Ghosts from a request that is never re-sent stay visible** in some permutations until a restart (and forever after a rebuild). The watermark filter hides history-graph ghosts with `recorded_position` above the watermark. It does not hide ghosts in an unversioned projection graph (section 7, failure case 3).
- **Timeouts do not bound update time.** An INSERT DATA with new terms ignored a limit 20 percent below its runtime. Set the HTTP client timeout, not the QLever `timeout`, as the bound, and expect the server to keep working after the client gave up (S5).

## 3. Group commit curve

### 3.1 Verdict

1. **Fixed cost per request is small at an empty delta and linear in the delta.** An update with no triples costs 2 ms at delta 0 and, on L, 22 ms at 100k, 115 ms at 500k, 203 ms at 1M. That is about 0.2 ms per 1,000 delta triples (metadata update, snapshot deep copy, file rewrite). R2's inferred 0.9 s fixed cost at 1M delta was too high by 4x to 5x on this layout.
2. **Marginal cost is about 0.025 to 0.03 ms per triple** (parsing 0.012, evaluation and delta insertion 0.006 to 0.008, plus consolidation).
3. **Largest batch wins.** Within the tested range (1 to 50k triples), triples per second rise with batch size at every delta, and the best measured cell is 43k triples/s (10k batch at delta 0), 38.5k triples/s (50k batch at delta 100k), 28.6k (50k at 500k) and 29.0k (50k at 1M) on L.
4. **Mid-size batches pay an extra cost that scales with touched blocks.** At 1M delta a 1,000-triple request costs 294 ms (203 ms fixed plus 27 ms of work expected, observed 65 ms more, in the metadata phase), so single transactions and small groups sit at 3 to 5k triples/s.

Confidence: High (7, 7, 7, 5, 3, 3 repetitions per cell, each delta exact because the server was restarted from a saved persisted file; noise about plus or minus 30 percent).

### 3.2 Evidence

Method: `scripts/p3_group_commit.py`. For each delta size D the delta was built with 25k-triple INSERT DATA requests from fresh C-layout facts (new assertion IRIs, new tx IRIs, new string literals, existing entity IRIs on L), the persisted file was saved, and every large-batch measurement restarted the server from that file so the delta was exactly D. The small batches (0, 1, 100, 1,000) ran in one process after a restart with at most 6k triples of drift. Client latency is wall time of the HTTP request; server phases come from the update response (`time` object). **Sustained fill rate.** Building the 1M delta with 25k-triple requests took 30 s on L (33k triples/s average) and 41 s on S (24k triples/s), with the average rising as the delta filled. The persisted file was 38 to 42 MB at 1M delta (about 40 bytes per triple), and the replay after a restart restored 1M triples in a few seconds (section 6).

**Fixed-cost model [E]:** `latency_ms ≈ 2 + 0.2 × (D / 1,000) + 0.027 × b` for b above 5,000, with a 30 to 60 ms surcharge for batches of 100 to 1,000 triples at D above 500k. Break-even batch (fixed cost equals marginal cost): 7.5k triples at D=1M, 4.3k at 500k, 0.8k at 100k.

### 3.3 Design implication

- **Group Triplex transactions into requests of about 10k to 50k triples.** At the rebuild-trigger ceiling of 1M delta, 10k triples reach about 12k triples/s (0.8 s per request) and 50k triples reach about 29k triples/s (1.7 s per request). One Triplex fact is about 8 triples in the PC layout (7 history plus 1 projection), so 10k triples is about 1,250 facts or about 250 transactions of 5 facts, and 50k triples is about 6,000 facts.
- **Budget for commit latency of group wait plus 0.3 to 1.7 s of server time**, rising with the delta. A single-transaction request costs 190 to 290 ms at 1M delta for about 40 triples, so a one-transaction-per-request design caps at 3 to 5 transactions per second per replica at 1M delta, and at about 25 per second at delta 0.
- **Keep the delta small.** Every 100k of delta adds about 20 ms to every request. Rebuilding at 250k instead of 1M cuts the fixed cost from 200 ms to about 50 ms (section 2 gives the rebuild cost).
- **Upstream will remove the delta term.** PR #3607 (snapshot creation proportional to the update, merged 2026-10-06) and PR #3267 (metadata update, open) report Wikidata updates at 500k delta dropping from about 700 ms to about 60 ms [W]. Neither is in 0.6.0.
