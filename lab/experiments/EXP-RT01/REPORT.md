# EXP-RT01 round A — builder report

North star: P1 immutable named recorded-time reads and P2 exact decided receipts. Scope and targets: `lab/SCOPE.md`, `lab/NORTH-STAR.md`, `lab/TARGETS.md`. Design: R33; rulings Q89a-i and Q90a-g. This is builder evidence, not independent qualification or promotion.

Implementation and final gate results are being completed. The oracle, golden vectors and generated contract are untouched. Round B and seals are outside this branch.

## PASS / receipt audit before the A0 source commit

- `core/storage/RecordStamp.ts`: conversions check safe integer range, inverse equality and quotient ordering; `gateRecordedAt` checks the observed watermark after both the initial read and wait, and returns a typed refusal otherwise. Its result is an available cut, not a semantic PASS. The cut comes from the requested scope on the executing read attempt.
- `core/store/transactionMetadata.ts`: journal v2 obtains the transaction's own instant from the persisted position fact; legacy v1 retains its original instant. It never invents an instant from the current clock on decode. Tests compare complete decoded changes with original expected content.
- `xtdb/XtdbStorageAdapter.ts` and `qlever/QleverStorageAdapter.ts`: commit success requires one marker matching this attempt ID, exact position and exact stamp (XTDB additionally reads operation ID). Guards bind the exact source position AND stamp; rows and the marker are submitted atomically in that guarded transaction. Random operation/attempt identities distinguish retries; transport success alone is insufficient. Readback tests check row, retirement and journal content against the returned receipt. Engine durability remains a live-gate obligation.
- `xtdb/Operations.ts` and `qlever/Operations.ts`: a `committed` resolution requires one durable operation marker with matching operation identity, valid attempt identity, positive safe position and exact stamp conversion. This deliberately returns the original durable receipt, not a claim that it was freshly committed during resolution. Scope and operation key bind the query.
- `testkit/route-equivalence.ts`: HE-1 to HE-8 compare content, exact basis echoes, forcing, availability, repeated served bytes and stamp order. The immutable execution plan binds input history, extension, requests and route policies; source hashes and the implementation commit bind the builder run. Offline-model results are explicitly not engine qualification. The staged-stamp control must still produce HE-5 and HE-8.
- `testkit/record-time-conformance.ts`, `record-time-schedules.ts`, `record-time-determinism.ts`, and new lane/core tests: assertions compare observed public bytes, receipts, history, refusals, reference stamps and repeated fresh fixture results. Live fixtures use fresh UUID scopes and fixed deterministic IDs. The offline XTDB transport interprets actual emitted guards/rows, but does not model an XTDB planner or durability. T8 is deferred-arm-only and is N/A on A0; legacy JSON decoding is covered separately by the core test.
- `run-gates.mjs`: records raw outputs, exact exit codes, dates, hashes and source hashes before/after; source drift fails the runner. An exit code alone is not a semantic verdict. `microbench.ts` checks receipt shape/content before recording measured durations, and emits measurements only, never an automatic performance PASS. Source snapshots preserve the main baseline.

First failures and incomplete attempts remain in `evidence/`. Cleanup targets only positively identified RT01 clients; it never changes resident engine lifecycle or deletes uncertain backend state.

The follow-up validation changes stream case progress into scope-bound JSONL, make the offline transport consume entity-list predicates used by real pagination, and run independent receipt readbacks concurrently without reducing the 200 disjoint / 50 contended write counts. A progress `completed` event is emitted only after the case's content assertions succeed; it carries this attempt's unique scope and encoding. It is not a whole-run PASS. The additional adapter microbench measures the actual XTDB A0 statement-building / receipt path with an offline transport; it retains the earlier core-only measurements rather than replacing them.

The final XTDB CAS uses one existing ASSERT for both coordinates (including compact encoding). A separate stamp ASSERT in the initial implementation was rejected because `XtdbClient.submit` would execute another PG-wire round trip. The focused offline protocol suite checks both coordinates in that one statement and still passes the concurrent schedules. Older live attempts do not certify this final statement shape.

The row-stamp invariant's hot path compares the supplied instant to the already validated memoized transaction stamp; only the first low-level stamp needs exact inverse conversion. A mismatched instant still fails before staging a row. This avoids repeating inverse validation for every journal and business row. Exact-conversion property tests and both actual-adapter offline protocols cover the change.
