# Full-size ceiling and cache locality

The verified 394 offered saves/s result used one gateway, one database, a ten-account 16,245,050-fact seed, one transactor core, Java 21 G1 and a 2 GiB transactor cache. It repeated a relatively small working set of people. At 235 and 394, every offer was durably accepted. The two busy cells recorded only 0.033 and 0.014 transaction-thread storage reads/save. The full-size ceiling is still open.

The ceiling command in the report restores the original pinned SCALE1 physical image once. Supply its original directory containing image.json, transfer.json and seed.pgdump, plus the two independently recorded metadata SHA-256s. Keep the original directory basename. The producer checks the pooled one-million-person, 162,456,470-fact proof at logical cut 87,002, the loader command and its stored journal claim, and every selected field predecessor at that cut. The stack verifies the physical dump digest before restore. Allow adequate PostgreSQL restore scratch as in the SCALE1 handoff. The command holds the full attempt to 60 minutes including restore and cleanup, with 12 minutes of offered traffic. No launch from this worktree targets a bench machine.

Run each pair for 90 s solo and 90 s loaded, in order 620/off, 620/on, 900/on, 900/off. Solo and loaded for each pair have the same 315 quiet offers. A loaded neighbour covers 1,900 distinct people, taken from separate deterministic bands scattered through the full 100,000-person account. The tape retains the field generator’s 415-save ordinal cycle. It traverses the active set repeatedly in each short window, with roughly 3–5 offers per neighbour’s active person. It does not simulate an entire day of edits for each person. The reader preloads the predecessor values at the sealed cut. That keeps those preloads out of the transactor and writer caches. Successive test cells still share global index and storage warmth. The order balances policy across the rates and does not make independently restored cold pairs.

Fair turns off allows 96 pending saves and rotates through ready accounts. Fair turns on issues at most six saves, with the quiet account reclaiming a turn when it has fallen behind, and waits for that turn’s receipts. Native Datomic can place one turn in several appends. The collector records those actual appends. The first solo cell must exercise the ordered fast path. Every committed candidate is checked against the exact queryable journal. The final output keeps in-window and drained counts, expiry reasons, people reached, SQL reads by seed or subsequent predecessor, append batch fill, apply and handoff tails, and three JVM safepoint logs.

Before the run, rough busy delivery forecasts at 620/900 offered are 450/520 saves/s off and 350/380 on. The 394 tape already needed 293 appends/s. At the same 1.344 saves per append these cells need 461/670 appends/s. Longer turns, cache misses on the scattered person reads, or durable append stalls could each keep delivered rates below those forecasts. Track quiet p99 as well as its matched solo ratio. ## Existing hashed IDs

No rewrite is required. The gateway looks up the current old assertion by the owner's EAVT and supplies its exact bytes for retraction. The ordered historical AVET range covers only the **new** assertion IDs. An old ID proposed as a new assertion still hits the same historical uniqueness guard. It is refused even after its retraction and even under a different owner. A noncanonical or mixed set of new IDs uses the exact legacy path. If the new assertion IDs form a canonical block, any historical matching ID inside that block is still refused.

The first replacement of a particular legacy field may incur a cold owner/row fetch. The next replacement of that field sees the last ordered row. There is no recurring historical legacy-ID probe caused by that original predecessor. A different still-legacy field can incur its own first predecessor lookup. Any person’s leaf can be cold again after eviction. Native retraction and redundant row lookups still run on every save. The mixed-format gate checks old → ordered → ordered, retained historical identity, exact prior bytes in the prepared retraction, and cross-owner retired-ID rejection.
