# Parallel preparation for the grouped writer

At 235 offered saves/s, 3,265 native groups with stage records spent a mean 39.40 ms in speculative Datomic evaluation, 0.18 ms materializing datoms and 4.55 ms awaiting the native reply. The complete gateway turn averaged 44.31 ms. At 394 offered, the matching values were 38.87, 0.22, 4.49 and 43.76 ms across 3,304 groups with stage records. The previous server campaign delivered 179.5 and 181.7 saves/s, with 7.97 and 7.99 saves per append. The clock recount hashes the original cell bytes against the verified archive, matches each acknowledgement to its stored receipt and counts each physical transaction's stage record once. 1. Give a bounded set of workers the same immutable Datomic basis for each next append. Form the cohort in the existing account-turn order. Run independent chains concurrently and keep the order of saves within each chain. Independence requires disjoint touched and read subjects, predecessor and retirement IDs, new assertion IDs, operations, commands and journal identities. A reference target, shared predicate or scope-wide dependency joins its affected saves to the same chain. Anything without a complete dependency set uses the current grouped evaluator.
2. Keep each worker's row changes and exact observations, with provisional entity references namespaced by the member that created them. At the gateway fan-in, check the complete dependency sets against each other, give members their final logical positions and clocks, and materialize once in the scheduled order. Preserve true predecessor bytes and the original record time of an assertion retired within the group. The final transaction still includes ordinary business rows, the ordinary journals, every command claim and ordered feed records. Retain the current native basis check and publish receipts from that single append's durable report.
3. Start with one append in flight and pool work only when requests arrive. Several independently prepared appends against the same native basis miss after the first commits. Combine certified work into one append, or discard the affected preparation if the basis moves. Count all discarded and repeated work. The quiet account takes its existing next ready turn behind the one active append. Bound each selected cohort with the current member and byte limits.

At eight saves per append, the 235-load model uses 39.40 ms of parallel work and 4.91 ms of remaining time. Two ideal workers give about 325 saves/s and four give about 542. Reaching 394 requires an effective 2.56× speedup in speculation and a mean turn below 20.30 ms. I predict 300–325 saves/s with two workers and 430–520 with four if groups stay near eight and storage can serve the parallel lookups. An increase in missed bases, shorter groups or a shared storage ceiling pulls these numbers down. Measure them on the same seal before making a capacity claim.

The first comparison should check byte-identical oracle results before pricing throughput. It should inject a same-subject chain, a history-ID collision under another owner, a claim phantom, a shared-target retirement, a dictionary change, an erase-generation change and an external commit between preparation and append. Record group fill, useful and discarded speculative work, wait behind the active append and matched quiet-account p99. This proposal is unimplemented.
