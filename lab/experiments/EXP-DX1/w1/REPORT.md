K is the default journal policy. It keeps a separate row for each change and each affected subject.
P is an opt-in experiment. It folds those rows into one saved record and restores them for journal readers.
The native one- and three-field saves wrote 16 and 24 records in K and 14 and 18 in P. The old count was 23 and 31.
Their stored values occupied 2,224 and 4,818 bytes in K, and 1,704 and 2,644 in P.
At 50 saves a second, an equal mix of small solo saves reaches eight billion records in about 87 days with K and 109 with P, starting at 480 million.
The lean native query endpoint declined K's individual rows. The same query returned both change facts in the legacy layout.
Some large batches lost tens of milliseconds getting updates to the peer. Most batches assembled replies in under two milliseconds.
Both server launch plans include the new arms. The long Mac storage comparison is queued.

**K and Q107-S.** `TX2_SAVE_LEDGER=1` shares the claim, journal and receipt entity for an eligible strict save. It drops two claim copies, the duplicate transaction ID and clock, the feed link, the journal position and the journal revision. Subject CAS and physical journal rows stay. Old and new records share the upgraded reader. The legacy `/q` query over `:f/attr` is the native control. Three field replacements already need 13 records for the business transitions, change triples and affected subject alone. Lean requires native-query coverage before a Q107-S acceptance claim.
**P and Q107a/Q107c.** `TX2_PACKED_JOURNAL=1` enables the shared metadata layout and tests packing a gapless, indexed run of journal IDs. Decoding the frame with the exact business assertions must give byte-identical original journal rows. Unsupported rows fall back to K. The frame reuses the lossless row compressor. In the codec fixture the selected values occupy 1,061/2,775 B for K and 598/750 B for P at widths one/three. The selected changes and changed subjects disappear from ordinary native storage and general pattern scans. Typed journal lookup, paging and owner history read the mixed representation. The owner history probe scans the journal at its pinned cut. Native application-log behavior is outside this lean prototype.
**Grouping.** One native instant and final high-water pair are shared per physical transaction. Each member retains both identities, a logical clock and position, three membership links and two touched-owner witnesses in this fixture. The interior-cut implementation writes a retirement marker per replaced row. The count model for N disjoint saves of w fields is `N × (15 + 5w) + 2` for K and `N × (15 + 3w) + 2` for P with gapless IDs. At the same mix and rate, large groups reach eight billion in about 70 and 83 days. The first P frame also sets a scope flag.

**Evidence rules.** Native parity checks positive and negative content, an exact test count, a fresh nonce, source/codec/JAR hashes and a fresh in-process slot. The census checks the current commit's historical datoms, matched journal and operation, source and attempt. Wire capture reconstructs the original request from both bodies on a nonce-bound socket and hashes SDK sources and inputs. SQL checks index coverage and exact journal data, receipts and pins from a restarted peer with the same hashed write witnesses. The analyzer binds SQL bytes to the staged source, attempt, image and reservation. Server summaries require durable readback, matching source/slot/nonce, seed digest and prediction bytes. The collector verifies raw hashes and resource cleanup.
**Receipt paths.** The solo path acknowledges the applied Datomic result. The grouped reply uses the actual transaction report and compares each member's committed position and clock with its authored result. Operation and claim recovery read the committed unique indexes at the chosen cut. Packed frames are written only after a round trip matches each selected original row and the transaction checks historical identity reservation.
