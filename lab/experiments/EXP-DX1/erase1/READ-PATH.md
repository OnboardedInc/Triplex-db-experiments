# Erasure on the DX-INT1 base

**North star** P1 and P2 measure whether erasure disturbs pinned reads and saves. P3 and P5 cover feed replay and Publish. The correctness floor is the publication boundary in [TARGETS §7](../../../TARGETS.md#7-erasure-semantics-codex-finding-8-rulings-q24), from [SCOPE](../../../SCOPE.md) and [NORTH-STAR](../../../NORTH-STAR.md).

The source inspected is DX-INT1 `d0a909ba484b085d012d1086914590f7e905bd27`. The product rule comes from Q24 and Q36f on main `a619d4eb4f85e5bfd8925f4a1c07379529c5e37d`. Q24 preserves assertion identities and intervals, with a typed `ErasedValue {erasedAt}` at every basis for reads starting after publication. Q36f makes an erased SSN produce its own task and block E-Verify submission. [Rulings](../../../acceptance/RULINGS.md)

| Take a request | The only native excision caller on this base is the legacy feed fixture. `feed-live/prepare!` creates a scratch scope, resolves the fact by `:f/id`, and transacts `:db/excise` on that fact entity with `:db.excise/attrs [:f.v/string]`. Its value datoms are selected across all time. Identity, attribute, subject, validity, and transaction annotations remain. The gateway `route-handler` has no person/attribute erasure route. `feed-live/resume!` checks replay after a JVM restart. | Start and wait for indexing | `prepare!` captures `basis-t` from the excision ACK, calls `d/request-index`, and waits up to 120 s on `d/sync-excise` at that exact t. The index job removes matching datoms from the new indexes and transaction log. Datomic retains its excision audit record. The gateway's `request-index!` uses `sync-index`, which is the ordinary indexing wait. | Read across the job | A fresh database value can still expose the data after request ACK and before the excision generation arrives. With that generation, a renewed database value can query its pre-erasure t and history without the selected datoms. `prepare!` checks current-root history only. A held native value can still reference old segments. Gateway `storage/begin!` and `held-db` retain the old immutable database, and `read-db` uses the handle when present. `Replica.snapshotAt` also holds state on the TypeScript side. These paths have no erasure invalidation. The magnitude of that window is a measurement question. An attribute-limited excision selects all row strings on each named entity. For a single value it also selects unrelated rows on that entity, so it cannot be applied directly under Q24. A whole-person inventory needs owned children, inbound links and copies on other owners, including packed references. Datomic component recursion follows native component refs. | Replay the application journal | Core `transactionMetadata.ts` writes value-bearing `:_tx/change` JSON. On lean scopes `journal/page`, `build-command`, and `build-entity` use the transaction's journal links and packed rows. The legacy fixture never excises those copies. Its erasure does not create a Triplex journal transaction, replace historical values with markers, or update the replica. Q49a calls for identity-only erasure events and marker substitution in earlier journal reads. The `actv-delta` key/mask path is a separate pilot. | Reclaim bytes | New roots and log chunks make old objects unreachable. `d/gc-storage` can later delete obsolete objects past its cutoff. Live Datomic guidance retains them for at least a month outside initial import. In SQL storage, deletion leaves PostgreSQL heap and TOAST tuples for vacuum. Reusable page space, smaller relation files after a rewrite, and recycled WAL are separate outcomes. WAL, replicas, backups and existing peer caches can retain copies after indexing. The base has no PostgreSQL-page, WAL or backup purge on the excision path. [Datomic GC](https://docs.datomic.com/operation/capacity.html#garbage-collection-for-live-databases) · [PostgreSQL vacuum](https://www.postgresql.org/docs/17/routine-vacuuming.html) · [SQL storage inventory](../../../research/R32-datomic-durable-storage.md#4-erasure) |
| Apply the erasure frontier | The frontier is the latest published erasure sequence, independent of requested data t. Every read, cache hit, native query, feed/journal replay and restore must apply through that sequence. Data pins remain exact modulo the marker. This base has a data-position frontier and a native excision wait, with no public erasure sequence, separate durable ledger, guarded outbox publication or restore replay. INT1 `activate` stamps `erasure: "fresh-synthetic-scope"`. R38's key sealing, masking and ledger describe a design.
