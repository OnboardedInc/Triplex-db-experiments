# DX-ERASE1 · Measurement and evidence

**North star** P1, P2, P3 and P5. Measure exact pinned reads, save tails, journal replay and Publish while Datomic works on an excision. [Scope](../../../SCOPE.md) · [Priorities](../../../NORTH-STAR.md) · [Targets](../../../TARGETS.md)

- Start each arm on an owned Datomic Pro 1.0.7745 / PostgreSQL 17 stack. The launcher binds the attempt, source files, built packages, gateway mount, peer JAR, image IDs, caps, slot owner and containers. Source changes during a run invalidate the source binding. The stack uses normal durable PostgreSQL writes.
- Seed the lab deep profile through the public TypeScript save path. The target cohorts have separate initial journal transactions so the excision can remove their packed journal rows without removing a bystander's change. Each field save retracts the prior two assertions and adds two distinct strings in one real Triplex transaction. This is a synthetic native cost experiment with application-level ids, refs and journal records. It prices excision of all the identified people's packed domain and dedicated journal row datoms. Attribution of mixed journal copies and output stores remains an application problem.
- Quiesce and index the seed, then run control and excision blocks with the same pinned read cohort, traffic shape and count. Samples run from the request to the returned read or save ACK on the driver clock. The excision block includes saves after a short job completes. The report separates that block from requests that touched the job or finished entirely inside its clock bounds. Each block uses one serial save stream and up to four closed-loop readers. These diagnose interference under the observed cap and load, independently of the P1/P2 load profiles.
- Excision starts at native transact submission. The ACK, `request-index`, and `sync-excise` at the exact excision t have separate timing fields. The fresh-root check includes current facts, the original as-of t, history and selected raw-log transactions. It is repeated in a separate JVM. A native old database object and an existing gateway snapshot handle provide positive readbacks after the barrier. Their last positive observation bounds how long a reader can still get the value.
- Vendor index logs give job counters when attached to the database and matching indexing t. The SQL key difference is a separate measurement and includes log and root objects. An index can read a segment and retain it unchanged. Written segment counts do not price every read. [Datomic metrics](https://docs.datomic.com/operation/monitoring.html#transactor-metrics)
- Measure PostgreSQL stored value, relation and allocated WAL bytes before and after a recent-cutoff cleanup on a disposable stack with released pins. Record ordinary `VACUUM` before the separate `VACUUM FULL` rewrite. The before/after collection includes superseded index generations created across the measured arms and the last ordinary indexing job. Older snapshots, backups and raw-media bytes are outside this observation. [Datomic GC](https://docs.datomic.com/operation/capacity.html#garbage-collection-for-live-databases) · [PostgreSQL vacuum](https://www.postgresql.org/docs/17/routine-vacuuming.html)

Run a local size with `node lab/bin/heavy.mjs --label DX-ERASE1 -- node lab/bin/engine.mjs erase1 --holder DX-ERASE1 --run scale --people 700 --out scale-repeat`. The output name must be fresh in the lab vault. Use `--run smoke --people 24` for the functional gate. The measured rungs use the shared measurement window. Build the public `core`, `datomic`, `qualification` and `w0` packages before starting.

Run `python3 lab/experiments/EXP-DX1/erase1/summarize.py ATTEMPT_DIR` on each settled attempt. It recomputes nearest-rank quantiles from raw requests, correlates the native `:excise/ents` and `:index/create-index` records by their exact t and rereads the fresh-peer and cleanup receipts. The narrower create-index window excludes time spent waiting for the first peer to adopt the root.

## Receipt audit

| Observation | Content, freshness and binding |
| --- | --- |
| Stack and cleanup | `local` verifies exact image IDs and the pinned Datomic jar, each mounted source hash, SQL version and durability settings, and container IDs, caps and attempt labels. Cleanup verifies removal by ID, checks the owned volumes and network, then releases the matching slot. |
| Seed and saves | `Fixture.write` verifies every new public assertion and returned ID, durable position progression and the input digest. The seed census checks independently computed deep-profile cardinality. `traffic` verifies the last command against its native journal receipt and reads the acknowledged assertion IDs at that exact cut. |
| Reads, index and log | `prepare!` checks current/historical canaries and target-only journal ownership. `eraseArm`, `observe!` and `freshPeer` use the same attempt scope and exact excision t. A held pin is checked against the original full row fingerprint. The new root and distinct JVM must lose every selected row in current, as-of, history and the selected log transactions. These are bounded observations under synthetic ownership, without an acceptance verdict. |
| Storage | `collect` reads the owned PostgreSQL table immediately before and after the scheduled GC, then after vacuum and offline rewrite. It records key removal, relation allocation and WAL separately. The original zero-deletion smoke observation remains in the evidence. |
| Import | `ImportRun.step` checks native ACK and journal bytes through the source binding and frame digest. `importWork` requires an acknowledged frame in the synchronization window. The narrower index overlap is corroborated by the exact native excision t and projected job clocks. `replayErased` checks the newly committed journal payload and a separate current gateway read against the exact synthetic field. |
| Publish | `publishWork` captures and checks the original cut and brackets the native deletion at the first real checkpoint. `activate` checks roster, receipt hashes and native outbox contents against the independent domain oracle. The SQLite observation compares the old projection to the original selected marker on that same cut. |
