# Shared removal record and protected value keys

The gateway can use its existing local test directory or a separate PostgreSQL removal authority. Configure the authority with `TRIPLEX_ERASURE_JDBC` and inject a base64-encoded 256-bit wrapping key through `TRIPLEX_ERASURE_WRAPPING_KEY`. Use a separate PostgreSQL database. Production backup policy must also keep that database and the independent wrapping-key custodian out of every Datomic restore.

The removal record, sequence and pending request live in the `triplex_removal` schema. PostgreSQL commits synchronously. The authority reads the pending request and head in one snapshot. A successful publication inserts one identity-only entry, advances the exact prior head and deletes its pending request in one transaction. Every gateway uses the same PostgreSQL advisory guard for publication and delivery. Each protected read verifies the current authority against the native database before using a cached reply or unsealing a body. During a Datomic restore the route stays closed until the current identity entries have been replayed.

Protected saves take a randomly generated key from a batch held in memory after a successful shared-store commit. The ordinary save does not write a key file or synchronously allocate an authority row. A process discards any unconsumed batch at loss. That can leave unused keys in the authority. Do not reclaim them until storage can prove no retained or pending assertion references them. A depleted batch refuses the protected save with a retryable failure. The independent worker replenishes the batch and removes published keys after the grace. Restart uses a fresh batch, with the prior ciphertext still pointing to the keys durably assigned before the old gateway died.

The local recovery check replaces the entire gateway container and retains the authority database. It tests a real Datomic backup before the removal, the same old and current basis after the restart, temporary refusal while native data is behind the authority, and the exact restored marker afterwards. It also reads a separate protected control and checks its original value at both bases. The key check requires live SQL key absence while the immutable encrypted body still exists.

The first small SQL recovery check removed the gateway's whole writable container, verified the unaffected value at both bases, and verified SQL key absence while ciphertext still existed. After restoring the old Datomic copy it first received the typed freshness refusal and then the exact marker after replay. The same SQL authority passed the complete thirteen-route regression. Its first exploratory save comparison verified 64 appends per block. The protected median moved by −14.66 ms against the earlier control and +9.65 ms against the later control. The divergent controls make the Mac figures diagnostic. The replacement rerun verified 64 writes per block with the per-person writer enabled. Median saves were 48.93 ms in the first control, 48.69 ms protected and 18.97 ms in the second control. The resulting −0.24 and +29.72 ms deltas leave the 0.3 ms target unresolved. The prepared arm uses 500 replacements per block.

The recovery evidence includes the fresh gateway identities, exact planted assertion and control, original pin, current sequence, removal transaction, native ciphertext check and separately bound old backup. The save check validates each observed receipt and stored row from this attempt and emits measurements. The sealed per-person gate also required two other receipts while the first protected plan was held. The old sequence was refused at position 7 with no durable receipt. All test stacks released their private containers, volumes and slots. [Evidence hashes](P3-AUTHORITY-SHA256SUMS)

## Rotation and price

A SQL DELETE alone leaves old wrapped keys in WAL, old SQL backups and free pages. The prototype uses one injected wrapping key. It does not meet the approved irreversible rotation deadline while any usable copy of that wrapping key survives. The observed live-store deletion proves lookup revocation. It does not prove cryptographic removal from an old authority backup.

In deployment, the key custodian needs a separate epoch per account, issued against the forward-only authority. Rewrap surviving keys in bounded committed batches, use the new generation for issuance, confirm the prior generation has no surviving key rows and destroy the prior wrapping key in the custodian. The custodian ticket must prove destruction even after an authority database restore. A gateway or recipient without a current verified authority waits or fails. Preserve the tombstones and their exact publication order during any migration from local storage.

A first planning range is 1–3 minutes per ten million surviving keys if a batched SQL rewrite sustains 55,600–166,700 rows/s. There are roughly 1 GB of raw key and handle bytes in this example before SQL diagnostics, row overhead and WAL. The range excludes key-custodian delay and gateway failover. Check rotation alongside quiet saves at the retained-history size, where the scan cost follows the surviving key count. The 15-minute window remains unverified by this prototype.
