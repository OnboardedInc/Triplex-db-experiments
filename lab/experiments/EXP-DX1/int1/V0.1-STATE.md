## Version 0.1 defaults

The scorecard defaults to `--writer subject`. It mints ordered 26-character assertion IDs, verifies the numeric owner and uses no prefetch hints. Use `--writer grouped` for compact K. Both keep the journal stored and queryable.

The default is supported by the paired correctness gates and the 2 GiB bare-metal comparison. At 235 and 394 offers per second, ordered saves delivered 234.90 and 393.92 with zero expiries. Grouped K delivered 147.03 and 155.38. Quiet-account p99 remains above its bar. Bench evidence is in `bm1/PREP1-STORAGE-READING.md` at `530b88a6`.

The scorecard and the integrated server runner default to `server`. The playground defaults to `laptop`, and the Mac gates use small reservations. At its default memory scale, the laptop playground pins Java 21 Serial GC. Both profiles keep PostgreSQL synchronous commit, fsync and full page writes enabled.

| Profile | Transactor cores · heap · object cache · cap | Write gateway cores · heap · cap | Read gateway cores · heap · cap | PostgreSQL cap |
| --- | --- | --- | --- | --- |
| `laptop` playground | 2 · 640 MiB · 64 MiB · 1,280 MiB | 2 · 352 MiB · 640 MiB | 2 · 352 MiB · 640 MiB | 256 MiB |
| `server` | 3 · 24 GiB · 16 GiB · 30 GiB | 4 · 4 GiB · 6 GiB | 1 · 3 GiB · 5 GiB | 8 GiB, 2 GiB shared buffers |

The server defaults to Java 21 G1 on all roles. Choose `--tx-jvm j25-zgc` to change the transactor alone, or `--jvm j25-g1` or `--jvm j25-zgc` to change all three. `--wal-directory DIR` selects an existing filesystem distinct from the Docker data store. The launcher verifies the filesystem before startup and the live WAL mount afterward. [Server command](../v01/SERVER.md)

## Full-size bare-metal observations

Ten accounts held 100,000 people each and 162,456,470 current facts in one database. All three arms used the ordered writer, fair turns, four write gateway cores, one read gateway core and 1,900 people per busy neighbour. See `scale1/SCALE-TUNE.md` at `64a76c50d` on DX-SCALE1.

| Transactor | Delivered at 394 / 620 offered per second | Loaded SQL reads/save | Quiet p99 solo → loaded at 620 |

| 1 core, 2 GiB cache, Java 21 G1 | 201.83 / 187.12 | 1.81–2.02 | 89.75 → 444.09 ms · 4.95× |
| 3 cores, 16 GiB cache, Java 21 G1 | 361.51 / 351.19 | 0.74–0.96 | 41.13 → 186.13 ms · 4.53× |
| 3 cores, 16 GiB cache, separate WAL, transactor Java 25 ZGC | 345.80 / 365.13 | 0.79–1.11 | 25.18 → 57.67 ms · 2.29× |

At 394 offered, the best arm delivered 361.51 saves a second and 2,565 of 35,460 offers expired (7.23%). The best measured quiet-account ratio at 620 was 2.29× against 1.25×. The combined WAL and ZGC arm changed both settings in the full-size run. The integrated profile still needs fresh and billion-record bare-metal results.

At 16 million facts, separate WAL reduced the 394-offer quiet solo p99 from 82.76 to 6.99 ms. Of the 17 remaining loaded appends over 20 ms, 16 overlapped a transactor safepoint. See `bm1/APPEND-TAIL-READING.md` at `31f33faf8` on DX-BM1.

## Owner decisions on November 21

- Version 0.1 uses failover Policy B. Reads continue after machine loss and saves wait for a verified second copy. This can exceed the 60-second save recovery bar at full size. Version 1.0 targets Policy C with three machines in separate failure domains.
- P6 meets the quiet-account commit bar at a loaded-to-solo p99 ratio of at most 1.25 or a loaded commit p99 of at most 50 ms. The paired sample and correctness requirements still apply.
- A lookup by the value of a protected field returns the typed refusal once the account has a removal policy.
- Server work comes before playground work. Bring forward the realistic seed with ten deep accounts, a wide thin account and 100 small accounts in one database. The two server campaigns here use the held ten-deep-account seed. The cloud budget stays at $200.
