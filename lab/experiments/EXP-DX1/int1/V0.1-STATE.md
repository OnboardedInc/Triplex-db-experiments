## Version 0.1 defaults

The scorecard defaults to `--writer subject`. It mints ordered 26-character assertion IDs, verifies the numeric owner and uses no prefetch hints. Use `--writer grouped` for compact K. Both keep the journal stored and queryable.

The default is supported by the paired correctness gates and the 2 GiB bare-metal comparison. At 235 and 394 offers per second, ordered saves delivered 234.90 and 393.92 with zero expiries. Grouped K delivered 147.03 and 155.38. Quiet-account p99 remains above its bar. Bench evidence is in `bm1/PREP1-STORAGE-READING.md` at `530b88a6`.

The scorecard and the integrated server runner default to `server`. The playground defaults to `laptop`, and the Mac gates use small reservations. At its default memory scale, the laptop playground pins Java 21 Serial GC. Both profiles keep PostgreSQL synchronous commit, fsync and full page writes enabled.

## Owner decisions on November 21

- Version 0.1 uses failover Policy B. Reads continue after machine loss and saves wait for a verified second copy. This can exceed the 60-second save recovery bar at full size. Version 1.0 targets Policy C with three machines in separate failure domains.
- P6 meets the quiet-account commit bar at a loaded-to-solo p99 ratio of at most 1.25 or a loaded commit p99 of at most 50 ms. The paired sample and correctness requirements still apply.
- A lookup by the value of a protected field returns the typed refusal once the account has a removal policy.
- Server work comes before playground work. Bring forward the realistic seed with ten deep accounts, a wide thin account and 100 small accounts in one database. The two server campaigns here use the held ten-deep-account seed. The cloud budget stays at $200.

### Recorded, not fixed

- **Removal policy and append retirement.** A declared removal policy excludes the append-retirement marker for the whole protected scope, including plain fields. The gateway guard (`subject_save.clj`) requires an absent erasure fence. So one estimate for a protected account cannot count both the policy and the native marker. The guarded saves were exact (DX-CHK1 `removal-c`, `read-c`). Owners: W1 and ERASE2.
- **Imports during a removal.** While a removal is in flight, imports receive the temporary typed refusal `ErasureFrontierUnavailable` (11 on the import route in DX-CHK1 `read-c`). The combined check's bounded retry kept the original grant, command and rows. The production import sender (`load1/fair-campaign.ts`) does not retry it and fails the run. Nothing is duplicated, since a frame is recorded only after its receipt. It cannot occur tonight because the removal stage runs alone. The production handling belongs to the import (HA1) and removal (ERASE2) builders.

### The server-32 profile

`server-32` is PREP1's measured cache32 arm under a name: transactor Java 25 ZGC, 48 GiB heap, 32 GiB object cache, 8 GiB direct memory, 60 GiB container. Cores, the write gateway, the read gateway, PostgreSQL, index settings and the separate write log are as `server`; `jvm1/server32.test.mjs` checks that it equals `prep1/rolling-launch.mjs`'s `1-rolling6-cache32-S` apart from its name.

- **Memory.** Role caps sum to 79 GiB (transactor 60, PostgreSQL 8, writer 6, reader 5); `server` sums to 49 GiB. With PREP1's 10 GiB host headroom the profile needs 89 GiB of MemTotal; a 96 GB machine has about 89.4 GiB. The stack start checks MemTotal on Linux. `launchProfile` refuses server-32 with a G1 transactor, with the 3 GiB read cache (83 GiB of caps) and with the tuned read study.
- **Scorecard.** `scorecard.mjs --profile server-32 --wal-directory DIR …` runs a full card with it; the profile is recorded in `input.json` and checked when the card is assembled. `--plan --profile server-32` prints the stages; only the transactor's memory, cache and flags differ from `server`.
- **Switching the default** is one line: `defaultServerProfile` in `jvm1/launch.mjs`. It moves the scorecard only. Other server runners name `server` directly and stay on it: `jvm1/cold-server.ts`, `jvm1/startup-server.ts` (its cache32 arms set `txCacheMiB` themselves), `v01/study-run.ts` and `study-server.ts`, `hasync1/pair.ts`, `erase1/measure-server.ts`, `actv-lazy/join/held-server.ts`, `int1/everything*.ts`.
- **Evidence for it at full size (430 million records, 2026-11-21, three transactor cores, rolling 6).** Three runs (cache32, cache32b, cache32c) stored 394.00/s and 620.00/s with no expiries. Second-half busy p99 at 394 was 521, 269 and 244 ms, and at 620 709, 725 and 711 ms. Quiet loaded p99 was 42.7 to 61.8 ms. Late SQL reads per save were 0.043 outside index jobs. Peak transactor cgroup memory was 51.2 GiB of 60. LOAD2's heap reading attributes the gain to the cache, not the heap. Nothing has run with it at 1 billion yet.

**If the default changes, these must be measured again with it:** the fresh card (P1 to P8), the 1 billion card and the realistic card; the quiet-account P6 ratios at 235, 394 and 620; P7 resident memory per untouched person at the transactor (48 GiB ZGC heap with uncommit); cold start and the start-up read (their launchers name `server`; their cache32 arms exist); the fair and live-first import arms (LOAD2's forecasts assume 16 GiB); removal on request at full size; the failover pair (both hosts need the 60 GiB transactor and the 89 GiB floor, and a standby rebuild restarts a 48 GiB heap); the read study; and the restart replay time.

### The aging loader's journal position rows (1 billion database)

All 28,222,864 saves the AGE1 aging loader made on the 1 billion database (positions 87,003 to 28,309,866) carry a `:_tx/position` row with the `-` header marker and the row's own position as payload. The product writes `P` and null. With the default reader, the change feed, transaction journals and row sweeps that cross that history throw (`Journal position payload must be null`); current, pinned and history reads of people and new saves work. The loader writes these rows through the gateway's test encoder `triplex.gateway.selftest/row-text` (`packages/datomic/gateway/src/triplex/gateway/selftest.clj`), called from `input` in `age1/src/triplex/age/tape.clj` and from `render` (through `journal-texts`) and `grouped-render` in `age1/src/triplex/age/native.clj`. **The loader must write canonical rows before it is used again.** The SDK reads the old rows only with the named option above.

The aged cache arm on this branch is PREP1's repaired one (admission at `1bbaf54cd`). The repaired `prep1/ceiling-seed.ts` and `jvm1/startup-aged.ts` share one spread that TypeScript narrows to `{ recorded_position }`; on this branch `startup-aged.ts` types it as a column record (`8805f75c9`); `ceiling-seed.ts` line 177 still has it and belongs to its builder. Runtime behaviour is the same.
