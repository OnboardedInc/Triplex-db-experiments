# DX-INT1 part 5 evidence

## One serving database

The native census keeps the same 200 deep people active while it imports up to 10,000, 30,000 and 50,000 in one database. It samples natural RSS three times at each cut, then records the live histogram, cache charge, and Native Memory Tracking before and after collection. It uses the same lean layout as part 4 for attribution. NMT measures JVM commitments and omits some native code and library allocations. It needs the resident samples for comparison. [HotSpot native memory tracking](https://docs.oracle.com/en/java/javase/21/vm/native-memory-tracking.html)

At 40,000 deep people the transactor's 1,020.79 MiB RSS includes at least 180.79 MiB outside the Java heap given the configured 840 MiB heap ceiling. The measured 181.194 MB object-cache cap was 99.6% filled. That bounds the cache charge and leaves open which pool added 39.38 MiB of RSS between 30,000 and 40,000. The trial used the JVM defaults for direct buffers and metaspace. The read gateway retained exactly 2,797 IDs and 1,136 row-cache entries at all three sizes. The old 2,000-person histograms show that touching 40 deep people could charge about 28.6 MB to the read peer's object cache. The fixed-activity histogram slope is still open. [Earlier observations](P4-EVIDENCE.md) · [Gateway histograms](GATEWAY-EVIDENCE.md)

Server peaks supplied in the brief were 2.55 GiB for one deep account and 4.67 GiB while loading ten. The saved staggered traffic pilot for ten 10,000-person accounts in one database reached 5.37 GiB in a 6 GiB transactor container. Its largest post-GC heap sample was 5.00 GiB, at its heap ceiling. The heap and container peaks are taken from separate counters. The size analysis puts the mixed storage footprint at 139–189 GB. Reserve 16 GiB for the mixed-load transactor as a planning estimate, with an 8–12 GiB `-Xmx` including 2.5–5 GiB of object cache and up to 1 GiB of memory-index novelty initially. Measure native commitments and indexing peaks against the process allowance. - The integration gates match the live engine lease, exact source archive, build-input and image hashes, and fresh native test output. The gate runner reopens those bytes before each branch push. The documentation-only reader handoff matches the tested runtime inputs byte for byte.
- The legacy campaign reader checks the actual scope on startup and rebuild. Its capability uses the validated journal bytes at the requested boundary and two fresh scope selectors with identical catalog rows and closure headers at the same position and native transaction. The frontier is checked before and after. The catalog proof reads no person rows. The erasure fixture binds its 13 route witnesses to a fresh native image, lease, seed and external-ledger sequence, with original backup bytes and a read-back restore.
- The memory verifier reads the actual compressed histograms, checks complete instance/byte totals and JVM native counters, and joins each sample to the same observed process, native image, attempt, original roster and native position. Attach snapshots are distinct from the prior natural RSS observations.
- The physical campaign checks the original dump's byte digest, source, original and new slot/nonce, population, and cut. The driver reopens every original seed claim and independently verifies the content before a restored arm is armed. A frozen and loaded pair shares the precise tape and seed receipt bytes.
- The saved-output gate checks all offered writer rows and their durable receipt identities, interval clocks, exact pinned rows, independent oracle, current feed and persisted resume. A new arm has fresh trace, scope and slot binding. The collector reopens the saved evidence and compares its output to the producer's. Field receipts separately verify native Publish coverage and import frame positions, commands and content. The physical launch reads JVM flags from the running process and joins the output to the captured container identity and pre-start clock. No short-run performance verdict is emitted.
