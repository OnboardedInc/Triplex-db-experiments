# Physical memory forecasts for P7

Collect three growing deep-population cuts in one Datomic database. Use the same accounts, touched identifiers, feed policy and JVM settings at each cut. Record the exact logical head, verified person count, process starts and cache limits. Take three natural RSS samples before attaching to a JVM. The read-gateway slope is the change between the final two median RSS values divided by the added untouched population.

| Open term | Forecast before the runs | What the physical census needs to check |
| --- | --- | --- |
| Deep read gateway resident growth | Under 64 resident bytes per added untouched deep person once the 32 MiB demand peer cache is full. | Check exact cache charges, admitted IDs and row counts, live heap, resident Java pages and native mappings at each cut. A reproducible late slope above 64 B/person would overturn this forecast. |
| Transactor residency after the object cache fills | 6–12 GiB peak on the shared deep and wide population. Provision 16 GiB for this census, with an 8–12 GiB heap, 2.5–5 GiB object cache within that heap and at most a 1 GiB memory index. | Record actual memory-index settings and indexing progress, independent object-cache charge, live and committed Java heap, direct buffers, metaspace, GC native allocations and process RSS. Check whether resident growth continues after the governed pools level off. |

At 10,000 and 30,000 deep people the read gateway live heaps were 62.06 and 61.68 MiB. The transactor gained 211 MiB of committed Java heap and 223 MiB of RSS. The archived ten-account pilot at 100,000 total deep people reached 5.37 GiB in its transactor container. The fixed-population scorecard pair cannot establish a marginal cost. Its current 6 GiB transactor container also constrains any peak it can observe. Record the separate physical census at each age alongside the card using the same schema and source.
