# Reliable save retries

1. Before sending a save, durably write its database scope, command ID, operation ID and complete submitted payload to the SDK's local pending store. Persist any ordering token the server requires. Keep one in-flight send per command. Reopen the pending store on process restart and restore the original identity and payload, including the predecessor, proposed time and values. A different edit needs a new command ID.
2. At the one-second caller deadline return `Pending` with the original command ID. The UI can say “Saving” and use that ID to watch for the receipt. A timeout, closed connection, failover refusal or ambiguous response leaves the command pending. Recheck or resend in the background with full jitter over a window starting at 250 ms, doubling to a five-second cap. Honor a longer server `Retry-After`. Keep the queue across restarts and offline periods.
3. Complete a pending save only on the original durable commit receipt from the same database scope and command. Check the transaction and operation IDs, then atomically save the receipt and remove the pending entry. A duplicate or stale-predecessor response triggers a claim lookup. A matching committed claim returns its original receipt. A definitive conflict after the original claim is checked can be shown as a rejected edit. If the claim check itself is unavailable, keep the command pending. Keep server claims available for as long as a client can retry.

The full failover drill seeds a value, commits a replacement and holds the successful reply until the primary has failed. A reader on the survivor must have seen the replacement before the cut. After promotion the test reopens the persisted pending record, resends the exact request bytes and requires the rebuilt client to return the original receipt. A second request with the original command ID and a fresh envelope reaches the native command guard. A genuinely different command naming the retired value must still conflict. The durable feed must contain exactly the seed and the replacement, and the independent replay oracle checks the reads on both sides of the edit.

The earlier scheduled traffic used append-only saves. Its `Account` helper could also resolve a stale-write response by looking up the operation. It did not establish this case. The source integration ports the native duplicate-before-predecessor guard and the older-gateway claim lookup from the write-path fix. The SDK pending store and its background scheduler are specified here. The failover gate uses a durable test pending record and the shipped command client.
