# The effects of data size and system count

The deep loads use the authored subject graph and canonical typed facts. Each fifth subject's placement status is retired and replaced three times. The loader compares the old and current values at their original cuts. Restore checks the retained receipt ledger and exact PostgreSQL backup manifest. In local runs, each exercised size shares one verified original checkpoint across the three arms. The index arm increases its recent log suffix with size while the withheld-reply and planned arms start from a fresh index, which lets the drills separate an indexed corpus from the work that needs replay after a fault.

The timing begins at the actual kill dispatch or the planned seal. The first on-time save sent after routing marks recovery. The native log records each replayed suffix's bytes and duration. Broker readiness and peer synchronization are distinct events. Rewind ends when the old disk starts as a standby, and the planned run requires a remote flush for the new save. A first read of each scheduled deep subject checks its typed values at the sealed cut. The client reports both its service time and time since routing. Read time is separate from writer recovery.

At the small size, log-window recovery and the planned move replayed about 19–53 kB in 4–20 ms. The corrected index fault replayed 2.35 MB in 189 ms. Broker readiness took roughly 10–16 s after promotion. Peer synchronization added about 0.8–5.1 s. The 0.85 s planned rewind fell between promotion and recorded broker readiness. The first wide index run spent 12 s at the gateway stage and remains in the record as an overload observation.

Forecasts assume no more than 40 MiB of native replay and up to 64 MiB of outstanding PostgreSQL WAL. A first save only needs recent Datomic log entries and the indexed paths it touches. Increasing the stored corpus can still enlarge the cold peer working set and the files PostgreSQL must inspect during rewind. At 16M facts I expect 12–30 s for a log-window crash, 15–38 s under an index crash and 18–30 s for a move. At 160M I expect 14–35 s, 17–44 s and 21–40 s respectively. The upper planned-move range misses 30 seconds. The fit reports milliseconds per doubling once at least two distinct edited rungs complete a drill. Treat it as descriptive with this sample size.

With one shared SQL pair, a single PostgreSQL promotion serves independently reconnecting Datomic transactors. With one SQL pair per system, each storage cluster promotes independently and competes for disk bandwidth. Shared schemas are the simpler starting design if the 10-system last-write time and resource limits hold. Use dedicated storage where one shared SQL cluster's I/O, administrative boundaries or common failure exposure matter. These tests use small cells and exercise recovery competition, so production sizing also needs the expected ongoing histories and workload mix.
