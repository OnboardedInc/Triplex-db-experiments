# Query surfaces the compact event preserves and gives up

**North star.** P1 exact coherent cuts, P3 dependency discovery and journal, P4 current pulls and P5 scoped release selection. [Scope](../../../SCOPE.md) · [Priorities](../../../NORTH-STAR.md) · [Targets](../../../TARGETS.md)

Datomic can index the event's account position, command, owner and predecessor. It can find a whole encoded body by event identity. A substring or a value inside that body never becomes an attribute or value in AVET. A query across people by an attribute, ref, equality or numeric range needs independently indexed facts or a scan and exact decode at a shared basis.

## The W0 reverse projection

Only placement-to-location and location-to-jurisdiction edges are materialized. The source feeds assertion/retirement coordinates, both validity endpoints and the account position. The projector places each mutation in one ordered AVET string under the source identity, account, relation, and target. It retains recorded history for exact old cuts. Direct owner candidates and reverse one- or two-hop lookups feed the W0 evaluator, which applies release-specific dependencies and excludes ballast. Census can enumerate placement roots from the owner index. The W0 affected operation ignores the request's valid time and evaluates dependency membership at the oracle's reference time. [W0 affected specification](../../../world/W0/SPEC.md#10-affected-set)

Each eight-event projector page costs one transaction instant and a watermark retract/add, plus one datom per reverse mutation. A one-edge replacement adds two datoms. The projector opens against a provisioned source identity and refuses a wrong database. While the watermark is behind, a reader folds the exact contiguous source suffix of up to 256 positions over that snapshot. A larger gap fails explicitly or can wait for catch-up. A newer index may answer an older cut by filtering on the original application coordinate, even within a physical group. The projector writes no protected values. Read and write costs of this retained posting history grow with churn on popular targets.

On Mac SQL, an empty watermark page averaged **0.375 datoms and 3 value B/save**. Replacing a reverse edge averaged **2.375 datoms and 201 B/save** at the median. The median projector time per save was 1.61 / 1.16 ms, measured as total page time divided by eight, in eight blocks per arm. Recorded save to published index lag was 24 / 18 ms p50 and 37 / 30 ms p99 over 64 saves per arm with immediate polling. The lag omits a production scheduler's polling and backlog. The exact overlay and caught-up index had identical candidate worlds on all nine affected fixtures, and their results matched independent O-DOMAIN. [Mac `p2-surface-b` evidence](SHA256SUMS)

## The journal that Q107-S requires

The base is 11 datoms for a solo save on an existing owner. For (n) asserted or retired facts and (c) distinct changed entities, stored lean journal adds one transaction entity ID, three ordinary rows for position, clock and command, (n) change rows and (c) ref rows. There is no mutable journal entity revision. That gives (15+n+c) datoms. Optional actor, correlation, causation and config metadata would add one row per supplied field. The one-, three- and 25-field replacement witnesses use (n=2,6,50) and distinct (c=1,3,25), for **18, 24, and 90 datoms**. Where all replacements change the same entity, those totals are 18, 22 and 66. Preserving legacy public IDs during migration needs an exact alias. The journal uses the source's numeric clocks, changes and original assertion coordinates while the envelope remains in place for recovery.

Those three solo witnesses measured 2,500 / 5,589 / 39,763 value bytes and 2,734 / 5,895 / 40,862 Fressian bytes, respectively. The one-field variant exceeds the original 2 KiB value budget using the incumbent-compatible lean row representation. The raw native query returned every changed-entity row and assertion and retirement from its acknowledged append. [Mac `p2-surface-b` evidence](SHA256SUMS)

The SIZE and RETAIN scenarios gave roughly 72, 181, and 271 days to 10B at 30, 12, and eight retained records per save. The same rate model applied to 18 and 24 records gives roughly 120 and 90 days before footprint and quiet-account limits are considered. Those are rate-model scenarios tied to a short observed production window. Under Q106f, deep accounts use isolated Datomic systems. Separate databases inside one shared storage role do not create that boundary.
