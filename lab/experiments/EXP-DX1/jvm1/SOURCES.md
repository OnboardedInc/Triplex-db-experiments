# What the vendor and operators recommend

- Datomic's transactor launcher starts from G1 with a 50 ms pause goal. A non-heap JVM argument replaces that launcher bundle in the pinned distribution. Our older SCALE1 command explicitly selects G1 and inherits HotSpot's 200 ms goal; the one-core peers may select Serial. For short saves, one collection can cover many scheduled commits. G1 adds concurrent work, which needs CPU even when its pauses are shorter. [Transactor reference](https://docs.datomic.com/operation/transactor.html#running-the-transactor) · [Oracle G1 defaults](https://docs.oracle.com/en/java/javase/21/gctuning/ergonomic-defaults-g1-gc.html) · [OpenJDK selection](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/share/gc/shared/gcConfig.cpp)
- Datomic recommends 32/512 MiB for the adaptive memory index. The threshold starts a job and the maximum imposes backpressure. Leave heap room above the sum of the object cache and the memory-index maximum. Size the transactor cache for hot uniqueness and index paths and leave room for transaction functions. Both peers also carry the memory index. Our SQL variants start jobs at 48, 128 or 256 MiB, so accumulated work and peer memory can be higher. More frequent jobs may cut long interference windows while increasing SQL I/O and repeated segment rewrites. The serial apply point still limits throughput. [Capacity planning](https://docs.datomic.com/operation/capacity.html) · [Background indexing](https://docs.datomic.com/indexes/background-indexing.html) · [Memory and caching](https://docs.datomic.com/operation/caching.html)
- Datomic documents default storage soft concurrency of 4 writes and 8 reads. The guide suggests more index parallelism when storage and spare cores can carry it. Its DynamoDB write-concurrency sizing reflects that service's provisioned capacity. Keep the SQL soft limits while measuring job duty cycle and transaction storage times. The vendor's peer cache and prefetch settings are process-wide. One reader-heavy peer can benefit from more cache while writer allocation and concurrent imports need headroom. Capture cache hits and SQL stalls before changing either pool. [Capacity planning](https://docs.datomic.com/operation/capacity.html#index-parallelism) · [Peer properties](https://docs.datomic.com/operation/system-properties.html#peer-properties) · [SQL storage](https://docs.datomic.com/operation/storage.html#sql-database) · [Monitoring](https://docs.datomic.com/operation/monitoring.html)
- Clojure/conj 2023 operators presented two experiments at Nubank involving fewer indexing jobs to reduce DynamoDB costs and ZGC on transactors. Their workload, storage billing and JVM differ from ours. The exact percentage throughput gain and daily job-count change are recalled figures and remain unverified here. The operator evidence makes cumulative index work and write amplification important countermeasures for the short-job hypothesis. A later operator talk describes Datomic in production at scale. [Palharini and Andrade, Operating Datomic at Scale](https://www.youtube.com/watch?v=bvEsnJiCs7E) · [Miller, Datomic at Nubank](https://www.youtube.com/watch?v=9kiuwsfCDFI)
- Datomic Pro explicitly added ZGC support on Java 25. OpenJDK introduced generational ZGC on 21, which is a JVM capability and a separate question from Datomic support. The JVM must have enough CPU and allocation headroom to let concurrent collection keep up. Keep the Java 21 transactor on G1 while the write-gateway collector study runs independently. [Datomic Pro 1.0.7705](https://docs.datomic.com/changes/pro.html#1-0-7705) · [JEP 439](https://openjdk.org/jeps/439)
- Oracle recommends keeping G1's adaptive young sizing. A pause goal guides collection and can reduce throughput when aggressive. Fixed initial/maximum heap and pre-touch trade startup and resident memory for steadier pauses. Large pages need actual reserved pages available to the JVM, permission and charge accounting. Explicit CPU count controls HotSpot's ergonomics but does not pin threads. The default CDS archive can reduce startup work and should be observed in the startup log; an application archive needs its own exact JDK and classpath evidence. [G1 tuning](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html) · [Java 21 launcher](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html) · [Default CDS archive](https://openjdk.org/jeps/341) · [Linux HugeTLB](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)
- Heartbeats and peer expiry are availability settings. The 5 or 10 second defaults do not explain a regular gap near 286 ms on their own. Datomic recommends investigating GC and memory before making them more tolerant. The local idle studies measured WAL sync and native wait contributions and qualified an early compilation hypothesis against two controls. The TCP-only result was within drift.
