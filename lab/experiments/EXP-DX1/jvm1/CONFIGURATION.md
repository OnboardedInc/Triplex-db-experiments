# Candidate for one Datomic database

The present arm reproduces the archived SCALE1 split placement and memory profile with its observed collectors spelled out. The Mac control uses the later small TAIL1 allocation. DX-TAIL1 owns the writer's choice of collector and its dedicated core comparison. All four DX-JVM1 arms keep Serial and one writer core. The candidate tests the other settings together before two sensitivity arms. All arms retain the same PostgreSQL durability, channel encryption and save path.

Core IDs describe a twelve-CPU placement. Verify that the chosen IDs represent separate available physical cores before comparing on an SMT host. Three transactor cores leave capacity for the serial apply thread, collector and indexing or storage handoff. Index parallelism stays at 1 while we measure job duration and duty cycle. A 32 MiB threshold aims to do less work per job; the 512 MiB hard limit protects peers and lets normal import bursts drain before throttling. Revert only the threshold to 128 MiB in the index arm. A smaller threshold loses if it increases cumulative job time, SQL traffic, slow saves or import interference.

Archived whole-run post-GC p95/p99/max occupancy in MiB was transactor 1,872/2,214/3,066, writer 1,275/1,561/1,724 and reader 1,824/2,592/2,616. Values come from completed GC summary lines with rounded occupancy, including setup and history. They provide sizing anchors, with live-set uncertainty from survivors, index buildup and the missing loaded-reader cohort. Heap maxima leave approximately 1.5/1.6/0.95 GiB above those observed maxima. The reader retains the larger peer cache for pinned reads and the writer trades cache for native and allocation headroom. Track cache misses, RSS peaks, allocation stalls and post-GC occupancy at the full multi-account rung before accepting these caps.

All candidate roles use an explicit available CPU count, tiered JIT with two compiler threads, scaling 0.1, automatic CDS and 256 MiB direct NIO caps. The compiler sensitivity returns all three to scale 1. HotSpot G1 uses its adaptive 5–60% young bounds. A fixed young size would limit the pause goal. Pre-touch only the server transactor's initial heap, then measure both startup and steady pauses. Check CDS mapping in startup output and measure restart to the first correct save from real offered work. Keep huge pages and THP requests disabled until the host reserves pages, the cgroup allows and accounts for them, and the live process confirms actual mapping. No application CDS archive is assumed. 10-second transaction deadlines and 5-second heartbeats retain the vendor defaults. Datomic's private SQL pool and gateway Jetty pool retain their existing settings pending an observed saturation mechanism.
