# Deep account profile, revision 1

Each Datomic database represents one account. A subject is one person and owns all of their placements, tasks, subtasks, field values, custom values and file references. The root and two history attributes retain the NS harness's original wire identifiers so every existing history and snapshot check has a real row to inspect. All values and identifiers are synthetic.

| Quantity | Input or choice | Representation |
| --- | --- | --- |
| People | Measured 100,000, growing by 62,000 per year with 1,800–8,800 new per month | A fixed 10k or 100k snapshot per scope. The 10k rung shortens seeding. Neither rung simulates a year of arrivals. |
| Placements | 1.8 per person | Alternate integer counts using cumulative floors. A person links to each placement. Tasks rotate evenly among their owner's placements. |
| Tasks | 5.7 per person, 38% incomplete | To make distinct small, medium and large reads, 10%, 80%, 3%, 6% and 1% of people start with 4, 5, 10, 11 and 34 tasks respectively. These invented weights give exactly 5.7. In each group of 50 task serials, a fixed permutation gives 31 completed tasks. An absent closure fact denotes an open task. |
| Subtasks | 5.5 per task | Alternating five and six. Parent references identify all steps, including pending steps. Each completed step carries a timestamp. Nested steps give 3, 4 and 6 reference hops with the original 40/35/25 sampling weights. |
| Field and custom values | 13.3 per task, 57 bytes per field, 6.6 custom values per person | Cumulative floors preserve the averages. Field payloads use 57 deterministic ASCII hexadecimal bytes. Actual field compressibility is unknown. Six or seven custom slots represent start date, pay, hours, wage floors, background status and classification, which supply the release inputs. |
| Files | 1.4 per person | Each reference leads to an object identifier and a synthetic expiry date. The stored population excludes file bodies. |
| Saves | Up to 37 saves per task | Each task gets a deterministic limit from 6 through 37. Six allows a separate save for each possible step. Open tasks start below that limit. A person edits three consecutive fields and a progress counter, with one receipt stamp. Steps close proportionally to save count. The final save closes the task. When no task remains open a new follow-up starts with its actual fields and subtask structure. |
| Other writers | Existing 40/30/10/20 split across people, systems, agents and runtime | The three machine roles update their own four typed signal, proposal or reconciliation attributes on a real task, plus the receipt stamp. A proposal has its own attributes. System retries, lost ACKs and 30-day corrections retain the original frequencies and delays. |
| Activity | Measured 1,900 daily, 38,000 in 30 days. Requested daily fraction 2%. | A fixed daily roster of 2% rotates across a seeded 38% monthly roster in 30 equally spaced steps. The Zipf exponent is 1.1. The 95% Zipf and 5% uniform choices both draw from the daily roster. The first account actually touches 200/200 or 1,989/2,000 eligible people in its timed prefix. |
| Rate | 1.6 total primary commands/s in a working period, per account on both rungs | Frozen independent Poisson streams per account. Bursts align across accounts at 50× for 60 s, starting at 120 s and every 600 s thereafter. Alignment tests a simultaneous rush. The separate optional ten-fact rate probe is off. The history and post-capture correctness writes are counted as overlays. |
| Retained history | Estimated 45–75 million facts/year from 14.6 million annual saves | The initial snapshot contains current state. Live updates retain retractions and prior values. Annual history and disk from file bodies are outside the measured denominator. |

The ordinary `deep` profile uses named `deep-10k` and `deep-100k` rungs, the frozen 7,200-second stream and v3's 5,910-second offer prefix. The frozen file records SHA-256 over ordered, full seeded subject rows and logical command bytes for every scope. The legacy v3 digest is independently checked. The 40-person `deep-smoke` rung exercises the normal entry point on a short functional schedule.

**Activation.** The dedicated stage creates an independently seeded deep database. It publishes R1, runs a 100-second presweep with 64 live readers, commits the R2 release, and evaluates and publishes all people at that exact cut while traffic continues. The same R1 and R2 releases change the I‑9 deadline, document expiry and wage floor. The projection uses the recorded placement start, pay, hours, background status, state and local floors, first task's progress, file expiry and one form answer per task. The generator assigns early November start dates, synthetic pay of 1,400–2,099 cents, 2,000–2,899 working minutes, and 1,500–1,999-cent floors. Odd/even people get March or December expiry dates, and the first and second files stand for an employment document and a visa. These choices give the three rules differing outcomes. A 32-person page bounds working memory. Ten post-capture changes challenge point-in-time reads. The post-run verification checks every projected result for both releases and every durable outbox state against O-DOMAIN. This stage has its own plan identity.

**Resource layout.** One PostgreSQL instance, transactor JVM and its object cache, and two gateway JVMs serve every database in a stage. The JVMs get separate physical CPU sets. PostgreSQL gets CPU 1, the transactor CPU 0, the write gateway CPU 2, and the read gateway CPUs 4–5. Per-scope senders share CPU 3 and their six reader workers share CPUs 6–11. Each account owns a Datomic database, a transactor thread pipeline, a writer, a feed checkpoint and witness store, a replica, reader caches, expected-state journal and independently bound oracle. The sender and reader allocation stays the same across one and ten. Numerical CPU identifiers are bench-local logical CPU indices. The controller verifies distinct physical cores. The driver and engine cgroups share the host's RAM, filesystem and devices.

The transactor heap cap is 5 GiB with a 2,560 MiB object cache. Each gateway gets a 4 GiB heap, a 1,536 MiB Datomic object cache and the existing 256 MiB entity cache. Each engine container is capped at 6 GiB. PostgreSQL uses 1 GiB of shared buffers and synchronous writes. Each reader's history window is 192 MiB and its world cache is 32 MiB. Per-scope V8 heap ceilings and the whole client memory ceiling are recorded on admission. Read latency includes the gateway fallback. Commit latency is scheduled offer to the final receipt ACK.

The seed measurement divides the change in `pg_database_size` by verified current business facts on a fresh stack. A separate volume delta includes allocated WAL and filesystem blocks. The client cgroup ceiling leaves room for all four 6 GiB engine cgroups and operating memory. The sampler records their combined usage at the same instant. Memory peaks, CPU usage, cgroup memory events, JVM GC heap observations, object-cache counters and PostgreSQL cache/I/O counters are recorded separately. A shared cache hit or an exhausted core cannot be attributed to a single account from these counters alone.

Admission reserves a 15 GiB disk floor, 5 GiB operating-memory headroom, 35% disk/spill and 15% memory margins. The first 10k trial starts with a 1,200-byte/fact storage estimate, a 16 GiB spill prior, 14 GiB for shared engines and 14 GiB for its driver. Later sizing uses measured peaks and allocated bytes. Ten full accounts require a completed single-100k measurement. If only seeding fits, bounded parallel waves record actual progress and the reason live traffic could not start.
